## О задаче

Решение закрытого соревнования на Kaggle «Следующий клик — Raiffeisen Bank Russia». Для каждого
клиента дана история событий в приложении банка: показы баннеров, переходы по экранам, клики. Нужно
предсказать, по какому из 32 продуктов клиент сделает следующий целевой клик (событие с кодом 469).
Перед целевым кликом организаторы вырезают из истории последние пять событий, так что самый
очевидный сигнал, то есть что клиенту показали прямо перед кликом, недоступен. Метрика — HitRate@1:
доля клиентов, у которых единственный предсказанный продукт совпал с ответом.

В train 100 000 примеров, в test 12 359, по одному на клиента. В справочнике 1 096 кодов событий,
и примерно у 80 % событий в историях продукта нет совсем: это экраны и действия клиента, а не
показы и клики по конкретному продукту.

Главная сложность задачи в том, что train и test получены в разных условиях. 7 апреля в 13:54 UTC
банк сменил режим показов: в test показы случайные, а в train нет. Данные train обрываются 6
апреля, а 97 % историй test заканчиваются уже после смены режима. Правило «клиент кликнет на то,
что ему показали последним» в train работает хорошо, но в test показы больше не несут знания
банка о клиенте, и это правило заметно слабеет. Большая часть работы ушла на то, чтобы найти и
использовать признаки, которые переживают эту смену режима.

Решение в двух словах: для каждого клиента все 32 продукта ранжируются градиентным бустингом
(LightGBM) по признакам истории клиента, популярности продуктов в банке и экранов, которые клиент
открывал перед кликом. Обучающих примеров больше, чем дано в train: каждый клик внутри историй
превращается в отдельный пример, а немногие клики, сделанные уже в новом режиме, получают
повышенный вес. Итоговый ответ — усреднение шести моделей.

подстраиваются под несколько сотен примеров нового режима так сильно, как модели с весами.

## Установка

Код проверялся на Python 3.14.0, версии зависимостей зафиксированы в `requirements.txt`.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

Вся обработка данных написана на `polars`. `pandas` нужен только в одном месте, чтобы передать в
LightGBM номер продукта как категориальный признак, `pyarrow` — для этой конвертации, а
`scikit-learn` — для интерфейса `LGBMRanker`. `ipykernel` нужен только для ноутбуков.
`matplotlib` и `seaborn` остались в списке с начала проекта и сейчас нигде не используются.

## Данные

Данные соревнования в репозиторий не входят. Их нужно скачать со страницы соревнования и положить
в папку `data/` в корне репозитория без изменений:

```
data
├── train.parquet              100 000 примеров: example_id, client_id, events, target_product
├── test.parquet               12 359 примеров: те же колонки без target_product
├── event_dictionary.parquet   1 096 кодов событий: тип (view / click / other) и флаг целевого события
└── sample_submission.csv
```

`events` — это список событий клиента, у каждого есть время в миллисекундах, код события и номер
продукта (у большинства событий номера продукта нет). Путь к папке вычисляется от расположения
`src/data.py`, поэтому скрипты можно запускать из любой директории.

## Запуск

```bash
python3 train.py
python3 predict.py
```

`train.py` строит признаки, обучает модели на части train и печатает качество на двух валидациях,
затем обучает финальные модели на всех данных. В `models/` сохраняются шесть моделей
(`ranker_w_{0,1,2}.txt` с весами, `ranker_{0,1,2}.txt` без весов) и таблицы контекста экрана
`context.parquet`, чтобы `predict.py` считал признаки по тем же таблицам. Обучение занимает около
пяти минут на Apple M4. Ожидаемый вывод:

```
51 признаков, 56809 доп. примеров, 803 апрельских
view    testlike 0.3913  april 0.4035
ranker  testlike 0.4684  april 0.5106
модели сохранены в models/ranker_*.txt
```

Первая строка качества — правило «продукт последнего показа», вторая — ранкер.

`predict.py` строит те же признаки для test и пишет две отправки в `submissions/`: `ranker_w.csv`
(среднее трёх моделей с весами) и `ranker_mix.csv` (среднее всех шести). Занимает около 15 секунд.

## Воспроизведение итоговой отправки

Итоговая отправка — `ranker_mix.csv`, private 0.40618. Вторая выбранная отправка — `ranker_w.csv`,
private 0.39905. Обе получены кодом из коммита с тегом `kaggle-final` (`b978060`). Более поздние
коммиты меняют только документацию и журнал отправок.

```bash
git checkout kaggle-final
python3 train.py && python3 predict.py
md5 submissions/ranker_mix.csv submissions/ranker_w.csv   # на Linux: md5sum
```

Контрольные суммы:

| Файл             | md5                                |
| ---------------- | ---------------------------------- |
| `ranker_mix.csv` | `d13b639fea94d9ad24201ca1e7deec57` |
| `ranker_w.csv`   | `416c9594f02cd8da42f59e5ed1b3ad06` |

Повторный запуск на той же машине даёт побайтово те же файлы. Для этого в коде зафиксированы все
источники случайности: сиды моделей и выборок, а также порядок строк перед каждой операцией, где
он влияет на результат. Например, `rank("ordinal")` при равных значениях смотрит на порядок строк,
а порядок после `group_by` в polars от запуска к запуску разный. Без сортировки перед рангом две
одинаковые сборки расходились в сотнях предсказаний.

Проверено на macOS 26.5, Apple M4, Python 3.14.0, LightGBM 4.7.0, polars 2.1.0. На другой
платформе или с другими версиями библиотек LightGBM может посчитать часть сумм с другой ошибкой
округления, и тогда у отдельных клиентов поменяется продукт при почти равных скорах. На других
платформах это не проверялось.

## Метод

### Постановка как ранжирование

Каждый пример превращается в 32 строки, по одной на продукт, и модель для каждой строки отвечает
на вопрос, насколько вероятно, что клиент кликнет именно этот продукт. Из кандидатов убираются
продукты, которые банк вообще не показывал в последние три дня (`views_3d = 0`): кликнуть их
клиент почти не может, а модели они только мешают. Примеры, у которых правильный продукт после
этого фильтра пропал, из обучения выбрасываются.

Модель — `LGBMRanker` с целевой функцией lambdarank, группа — один пример. Ранкер напрямую
учится поднимать правильный продукт наверх внутри клиента, а для HitRate@1 важен только верхний
продукт.

### Обучающие примеры

Кроме 100 000 размеченных примеров train, обучение использует клики внутри историй. Каждый
целевой клик в середине истории превращается в новый пример так же, как это делают организаторы:
история до клика без последних пяти событий, ответ — продукт клика. Берутся клики, перед которыми
есть хотя бы 30 событий. Из train берётся один случайный клик на клиента, из test — все.

Клики из test-историй особенно важны. Это единственные размеченные примеры, снятые после смены
режима показов, то есть в тех же условиях, что и сам test. Их несколько сотен, и поэтому они
получают повышенный вес (см. ниже).

### Признаки

Всего 51 признак. Их можно разделить на шесть групп.

**История клиента по продукту** (`src/features.py: history_features`): сколько раз был каждый из
восьми самых частых кодов событий с продуктом, сколько кликов любого вида, сколько событий за
последний час и сутки. Сколько секунд прошло с последнего и первого события, с последнего показа
и клика. Ранги свежести внутри клиента: `rk_13 = 1` у продукта, который показали последним, то
есть само правило «последний показ» модель получает как признак. Сюда же относятся число
показов продукта среди последних 5 и 20 показов клиента и доля продукта в показах клиента по
отношению к его доле в показах всего банка за 7 дней (`share_13`, `lift_13`).

**Клиент целиком:** длина истории в событиях и во времени, число показов, со сколькими продуктами
был контакт. Эти признаки одинаковы для всех 32 строк клиента и задают контекст для остальных:
`rk_13 = 1` у клиента со ста показами и у клиента с пятью значит разное.

**Популярность в банке:** число показов продукта за последние 3 дня, его доля среди всех показов
банка за 3, 7 и 28 дней и отношение трёхдневной доли к 28-дневной.

**Свежая популярность** (`fresh_popularity`): доля продукта среди показов банка за 24 часа до
и 24 часа после конца истории клиента, посчитанная по часам, и отношение этих долей.
Дневные окна после смены режима ещё три дня смотрят в старый режим, а под них попадает около 30 % test. Почасовое окно «после»
видит новый режим сразу. Утечки ответа здесь нет: истории всех клиентов test выданы целиком,
окно считается по показам всего банка, и доля самого клиента в нём порядка 5·10⁻⁵. Эта группа дала
самый большой прирост на testlike за проект, около +0.02.

**Показы после последнего клика** (`add_since_click`): сколько раз продукт показали после
последнего целевого клика клиента (если кликов не было — за всю историю), какую долю показов он
занял и сколько времени прошло с клика.
Это то, что банк показывает клиенту «сейчас», в отличие от всей накопленной истории.

**Контекст экрана** (`context_tables`, `add_context`): признаки по событиям без продукта. Для
каждого кода события и продукта считается лог-лифт: во сколько раз чаще обычного кликают этот
продукт, если среди последних 1, 5 или 20 событий клиента был такой код. Признаки `ll1`, `nb5`,
`nb20` — суммы лог-лифтов по кодам из хвоста истории. Таблицы строятся по примерам train и кликам
из train-историй. Частоты сглаживаются к общей частоте продукта с весом 30, чтобы редкие коды
не давали шумных лифтов. Таблицы считаются вне фолда: клиенты
разбиты на пять групп по `client_id % 5`, и пример получает таблицу, посчитанную без своей группы,
то есть никогда не видит собственный ответ. В новом режиме показы перестали нести знание банка о
клиенте, а экраны, по которым клиент ходит перед кликом, остались. Поэтому вместе с весами нового
режима эффект этой группы заметно сильнее, чем без них.

### Веса примеров

Пример с кликом после смены режима получает вес 20, с кликом после конца train, но до смены
режима — вес 5, остальные — 1. Значения подбирались по валидации на кликах нового режима:
веса 10 и 40 дают результат в пределах шума, 100 — не лучше, 200 — хуже.

На каждый из трёх сидов обучаются две модели: с весами и без. `ranker_w.csv` усредняет три модели с
весами, `ranker_mix.csv` — все шесть.

### Модель

`LGBMRanker`: 300 деревьев, learning rate 0.05, 63 листа, не меньше 50 объектов в листе,
подвыборка строк и признаков 0.8. Номер продукта передаётся как категориальный признак. Сиды 0, 1,
2. Скоры модели внутри примера переводятся в вероятности через softmax, вероятности моделей
усредняются, ответ — продукт с наибольшей вероятностью. При равенстве берётся продукт с меньшим
номером.

### Валидация

Используются две валидации, и ни одной из них по отдельности недостаточно.

**testlike** — последняя неделя train: модель учится на всём, что раньше, а оценивается на
примерах, у которых ответ входит в число продуктов, показанных в апреле. Это 13 812 примеров, шум
около ±0.003, но всё это старый режим показов.

**april** — клики внутри test-историй после конца train, 803 примера. Модель на валидации их не
видит. Это ближе к условиям test, но примеров мало, и шум заметно больше.

Последние изменения (веса, показы после клика, контекст экрана) дополнительно проверялись на 408
кликах после смены режима с кросс-валидацией по пяти группам клиентов. Код этой проверки в
репозиторий не вошёл.

## Что не сработало

Всё перечисленное проверялось и не дало прироста больше шума или ухудшило результат:

- поправка скора на частоту показов продукта (отправка 7): и на public, и на private чуть хуже,
  чем без неё;
- бинарная классификация вместо ранкера, модели крупнее и мельче текущей;
- больший вес свежим примерам старого режима и обучение только на последних неделях train;
- тренд популярности за 7 и 28 дней, CTR продукта, час и день недели;
- переходы «после продукта A чаще кликают продукт B», общие и личные для клиента;
- более короткие окна свежей популярности, 1–2 часа вместо 24;
- вес примеров нового режима 100 и 200 вместо 20.
